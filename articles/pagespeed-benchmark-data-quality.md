個人開発しているSEO診断ツールのコンテンツ用に、日本の人気サイト1,000件のPageSpeed Insightsスコアを一括計測しました。

集計したら、TBSがモバイル性能**100点**で堂々の1位でした。

……テレビ局のサイトが、画像も動画も広告も載っているあのサイトが、100点。

おかしいですよね。**おかしかったです。** この記事は、その原因を追いかけて計測基盤を2回作り直した話です。結論から言うと、**計測対象URLの検証を省いたことが原因**でした。

計測スクリプト（`benchmark_sites.py`）の要点は、この記事の中で抜粋しています。

---

## なぜ計測したのか

運用しているSEO診断ツール（[seoshindan.com](https://seoshindan.com/)）は、公開から4ヶ月（2026年7月時点）で診断実行が**16件**でした。ほぼ誰にも使われていません。

一方でブログ記事は39本あるのに検索流入がほぼゼロ。原因は明確で、「titleタグとは」「被リンクとは」といった**どこにでもある解説記事**しか書いていなかったからです。同じ土俵で新規ドメインが大手SEOメディアに勝つのは無理があります。

そこで方針を変えました。**他所にない一次データを持つ**ことにしたわけです。

最初は「自分のツールの診断データを集計して記事にする」つもりでした。が、DBを見たら `url / domain / status / duration_ms` しか保存しておらず、**スコアを計算後に捨てていました。** しかも16件では2年待っても記事になりません。

ならば自分で測ればいい、という話です。

## 対象の選び方

「日本の人気サイト」を恣意的に選ぶと、記事の説得力がなくなります。「なぜこのサイトを選んだのか」に答えられる必要がある。

使ったのは [Tranco](https://tranco-list.eu/) です。複数のランキングを合成した研究用のドメインランキングで、CSVで公開されています。

```python
rows = []
for line in raw.splitlines():
    rank, domain = line.split(",")[:2]
    if domain.endswith(".jp"):
        rows.append((rank, domain))
```

上位100万件から `.jp` を抽出すると **16,667件**。その上位1,000件を対象にしました。

これなら記事に「Trancoランキング上位の.jpドメイン1,000件」と手法を明記できます。恣意的な抽出だと言われる余地がない。

## 1回目の計測：43%が失敗した

PageSpeed Insights APIを叩くだけの単純な処理です。並列8、リトライ2回、タイムアウト120秒。

```python
params = [
    ("url", f"https://{domain}/"),
    ("strategy", strategy),
    ("key", api_key),
] + [("category", c) for c in CATEGORIES]
```

2,000リクエスト（1,000ドメイン × モバイル/PC）を投げて、結果はこうでした。

```
■ 計測数: 2,000 リクエスト / 成功 1,137
■ 失敗の内訳
   827件  FAILED_DOCUMENT_REQUEST
    18件  NOT_HTML
    15件  NO_FCP
```

**43%が失敗。** 失敗の大半が `FAILED_DOCUMENT_REQUEST`（ページを取得できなかった）です。

最初は「そういうものか」と思いました。人気ドメインには広告配信用やCDN用のものが混ざるので、Webサイトでないものが弾かれるのは自然です。

しかし失敗リストを見て手が止まりました。

```
1637 jra.go.jp
2678 nhk.or.jp
3679 mhlw.go.jp
4487 u-tokyo.ac.jp
6040 kuronekoyamato.co.jp
```

**NHK。厚労省。東大。ヤマト運輸。** どう見ても普通に動いているサイトです。

### 原因：apexドメインにAレコードがない

DNSを引いたら一発でした。

```
$ getent ahostsv4 nhk.or.jp        → なし
$ getent ahostsv4 www.nhk.or.jp    → 23.55.208.230
```

**apexドメイン（wwwなし）にAレコードが存在しない。** `www.` でしか名前解決できません。厚労省も東大もヤマトも同じでした。

自分のスクリプトが `https://{domain}/` を決め打ちで叩いていたので、当然失敗します。**サイト側の問題ではなく、こちらのバグ**でした。

`www.` へのフォールバックを足して再計測したところ、失敗は863件→325件に減りました。ここまでは順調です。

## 2回目の計測：TBSが100点になった

再計測後の上位を見て、冒頭の違和感に戻ります。

```
■ パフォーマンス上位10サイト（mobile）
  100点  tbs.co.jp
  100点  rsch.jp
  100点  nuro.jp
  100点  weblio.jp
  100点  benesse.ne.jp
```

TBS、So-net（nuro.jp）、Weblio、ベネッセ。**大手が軒並み満点。**

実際に叩いてみます。

```
$ curl -o /dev/null -w "%{http_code} / %{size_download}B\n" https://tbs.co.jp/
404 / 872B
```

**872バイトの404ページでした。**

```
weblio.jp  → 404 /   236B
nuro.jp    → 403 /   202B
benesse.ne.jp → 200 / 1,018B（リダイレクト用スタブ）
```

つまりこういうことです。

1. apexドメインは実サイトを返さず、404やリダイレクト用の極小ページを返す
2. Lighthouseはその極小ページを**正常に計測する**
3. 数百バイトしかないので、当然すべての指標が最速になる
4. **100点**

`www.` フォールバックは「apexが**エラーを返したら**www.を試す」実装でした。apexが200や404を返して**計測自体は成功する**ケースは想定していなかったわけです。

そして厄介なのは、これが上位10件だけの問題ではないことです。**同じ現象が数百件で起きていれば、分布全体の「速い側」が押し上げられます。** 平均も中央値も信用できない。

危うく**存在しない404ページを「日本最速のサイト」として記事で紹介する**ところでした。

## 修正：計測前にURLを検証する

まずPSIのレスポンスからHTTPステータスを取れないか調べました。`http-status-code` という監査項目があるはずです。

```python
r = httpx.get(PSI_ENDPOINT, params=[("url","https://tbs.co.jp/"), ...])
# → HTTP 400（この時は別の理由で弾かれた）
```

再現性が安定せず、PSI側の情報に依存する設計は脆いと判断しました。**自前で検証する工程を前段に置く**方針に変えます。

計測を `resolve`（対象URL確定）と `run`（計測）の2フェーズに分離しました。

```python
async def resolve_one(client, semaphore, rank, domain):
    """apex → www の順に実際にアクセスし、実サイトと言えるURLを決める"""
    candidates = [f"https://{domain}/"]
    if not domain.startswith("www."):
        candidates.append(f"https://www.{domain}/")

    async with semaphore:
        for candidate in candidates:
            response = await client.get(candidate, follow_redirects=True, ...)

            if response.status_code != 200:
                last["reason"] = f"HTTP {response.status_code}"
                continue
            if "html" not in response.headers.get("content-type", "").lower():
                last["reason"] = "not HTML"
                continue
            if len(response.content) < MIN_CONTENT_BYTES:
                # 404ページやリダイレクト用スタブ。計測すると不当に高得点になる
                last["reason"] = f"too small ({len(response.content)}B)"
                continue

            return {"url": str(response.url), "ok": 1, ...}

    return {"url": None, "ok": 0, ...}
```

判定条件は3つです。

| 条件 | 理由 |
|---|---|
| HTTP 200 | 404/403ページを除外 |
| Content-Type が HTML | API・画像・DNSサービス等を除外 |
| 本文 2,000バイト以上 | リダイレクト用スタブを除外 |

閾値の2,000バイトは、実測した `tbs.co.jp` 872B / `weblio.jp` 236B / `nuro.jp` 202B から決めました。実サイトのトップページで2,000バイトを下回ることはまずありません（最小だった `mensnet.jp` で3,608B）。

`run` フェーズは確定済みURLだけを計測します。**URLを推測する処理を計測側から完全になくした**のがポイントです。

対象外になったドメインも理由付きで残しました。記事に「1,000件中272件は計測対象外（うちDNS解決不可159件）」と書けるようにするためです。

## 副産物：65.5%が「www」必須

計測とは別に、はっきりした事実がひとつあります。

**計測できた728サイトのうち477件（65.5%）は、`www.` を付けないとアクセスできませんでした。**

```
https://example.jp/      → つながらない
https://www.example.jp/  → 表示される
```

apexドメインにAレコードがない、あるいは404を返す構成です。歴史的経緯やCDN構成の都合なのでしょうが、想像よりずっと多かった。

外形監視やクローラーを書く人は、**apex決め打ちにすると3件に2件を取りこぼします。**

## 学んだこと

### 1. 「取得できた」と「正しく取得できた」は違う

一番効いた教訓です。HTTP 200が返ってきても、Lighthouseがスコアを返してきても、**それが測りたかった対象とは限らない。**

しかも今回の失敗モードは意地が悪い。エラーで落ちるなら気づけますが、**404ページは「非常に良いスコア」として静かに混ざります。** 例外も警告も出ません。

### 2. 外れ値は疑いのきっかけとして優秀

TBSが100点という結果に違和感を持ったのが唯一の入口でした。もし1位が「聞いたことのない企業のサイト」だったら、たぶんそのまま公開していたと思います。

**ドメイン知識のある人が結果を見る**工程は、自動テストでは代替できません。

### 3. 検証は前段に置く

修正前は「計測してから結果の妥当性を判断する」構造でした。これだと判断ロジックが後段に散らばります。

**計測対象を確定させるフェーズを分離**したことで、`run` は「渡されたURLを測るだけ」の単純な関数になりました。副次的に、対象外の理由が構造化データとして残り、記事に「N件中M件が計測対象外、内訳は…」と書けるようになったのも大きい。

### 4. 失敗の内訳を捨てない

1回目のとき、失敗を件数だけ集計していたら `nhk.or.jp` に気づけませんでした。エラー内容とドメインをDBに残していたから、`ORDER BY rank` で並べて異常に気づけた。

**「失敗しました」で終わらせず、何がどう失敗したかを残す。** 当たり前ですが、使い捨てのスクリプトほど手を抜きがちなところです。

## 追記（2026年8月）：この後さらに2つ、地雷を踏んだ

この記事の下書きを書いたあと、同じ仕組みで**自治体サイト67件**（47都道府県＋20政令市）を計測して記事にしました。そこで、上の「学んだこと」がまだ甘かったと思い知る出来事が2つありました。

### 地雷1：httpxで検証しても、Lighthouseは別のページを掴む

ある県のサイトに、モバイル性能**100点**がついていました。記事に載せて公開したあと、自分の診断ツールで測り直したら**39点**。個別サイトの点数を全て撤回するはめになりました。

`resolve` フェーズの検証（HTTP 200・HTML・2,000バイト以上）は通っていました。httpxで取りに行くと本物のトップページが返ってくる。ところがPSI（Lighthouse）からのアクセスには、中身のない極小ページが返っていたのです。bot対策か、障害時の代替ページだと思われます。

**自分のHTTPクライアントが見た姿と、Lighthouseが見た姿は別物**でした。前段の検証だけでは、この失敗モードは防げません。

対策として、Lighthouseが実際に読み込んだバイト数（`total-byte-weight` 監査の `numericValue`）を結果と一緒に保存し、**10万バイト未満なら「実体のないページを測った疑い」として警告**するようにしました。実際、動画配信サービスや不動産大手で「Lighthouseには32KBや8KBのページしか返らず、スコアは100点」という例が見つかり、計測不能として除外しています。

```python
"total_bytes": numeric("total-byte-weight"),  # Lighthouse が実際に読んだバイト数

MIN_MEASURED_BYTES = 100_000  # これ未満は空ページを掴んだ疑い。記事に使う前に手で確認する
```

### 地雷2：PSIは短時間の再リクエストにキャッシュを返す

個別サイトの点数はブレるので、「1サイトにつき3回測って中央値を取る」実装にしました。ところが、3回とも**同じ値**が返ってきます。レスポンスの `lighthouseResult.fetchTime` を見ると3回とも同一でした。**PSIは同じURLへの再リクエストに対して、しばらくキャッシュした結果を返す**のです（手元の観察では約90秒後に初めて再計測されました）。

つまり「1件ずつ3回連続で呼ぶ」実装は、**1回の結果を3回受け取っていただけ**でした。

修正は単純で、**全サイトを1周してから次の周に入る**方式に変えました。1周が数十分単位なので、周と周の間隔が自然に空いてキャッシュが効きません。各周の結果は別テーブルに残し、最後に中央値を作ります。

### 本当の3回計測で分かった、スコアのブレ

キャッシュを回避した「本物の3周計測」で、67サイトの3回の値がどれだけばらついたかを集計した結果です。

| 指標 | 値 |
|---|---|
| 3回の値の幅（最大−最小）の中央値 | 6点 |
| 幅が10点以上あったサイト | **39.4%** |
| 最大の幅 | **35点** |

あるサイトは36点・69点・70点という3つの値を出しました。一方で、**67サイト全体の中央値は何度測っても53点前後で動きません。** 個々のブレは、束ねると打ち消し合うからです。

ここから引き出した運用ルールはこうです。

- **集計値（中央値・分布・合格率）は1回の計測でも信頼できる**
- **個別サイトの点数やランキングは、3回計測の中央値でないと出せない**。しかも `total_bytes` が妥当な行に限る
- 記事に個別サイト名を出すときは、中央値の材料回数（`runs` 列）が3以上であることを機械的に確認する

この記事の728件の集計値は1回計測ですが、上の理由で集計値としてはそのまま使えます。TBSの「37点」のような個別の値は、10点程度の幅があるものとして読んでください。

### 定点観測は自動化した

当初は「3ヶ月後にそのまま流す」つもりでしたが、結局GitHub Actionsで**毎月1日に自動計測**する形にしました。対象は自治体67件を含む12業界215サイトで、各サイトを3周計測した中央値をCSVとしてリポジトリにコミットしています。8月と9月の2ヶ月分が貯まったので、前月比が出せるようになりました。
