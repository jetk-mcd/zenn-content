日本の有名サイト215件（自治体・テレビ局・電子書籍ストアなど12業界）の表示速度を毎月定点観測する仕組みを作っています。PageSpeed Insights（PSI）APIで一括計測してランキング記事を書く、というものです。

初回の記事を公開したあと、読者から「この自治体が100点になってるけど、実際に測ったら56点だったよ」という指摘をもらいました。調べた結果、**PSIの計測には落とし穴が3つある**ことが分かりました。どれも「1回測って数字を信じる」と踏み抜きます。

この記事はその検証ログです。

## 落とし穴1：Lighthouseが「実体のないページ」を測って満点を出す

問題の自治体サイトを再計測すると41点。100点はどこから来たのか。

保存していた計測結果を見ると、`total-byte-weight`（Lighthouseが実際に読み込んだ総バイト数）が異常でした。

| サイト | 記録されたスコア | total-byte-weight |
|---|---|---|
| 問題の自治体サイト | 100 | 数KB台 |
| 某不動産大手 | 100 | **8 KiB** |
| 某動画配信サイト | 100 | **32 KiB** |

普通のサイトは数百KB〜数MBあります。8KiBは「ほぼ空のページ」です。障害時の代替ページやJSシェルだけを掴むと、**中身が無いので爆速判定＝満点**になります。

しかも質が悪いことに、この3サイトはブラウザ（curl含む）でアクセスすると数百KBの実ページを返します。**自前のHTTPクライアントでの事前検証は通るのに、PSI（＝Googleのデータセンター）からのアクセスにだけ極小ページを返す**構成だったわけです。

### 対策

計測結果に `total-byte-weight` と `finalUrl` を必ず保存し、閾値（私は100KB）未満の行を警告するようにしました。

```python
audits = lighthouse_result["audits"]
total_bytes = audits["total-byte-weight"]["numericValue"]
final_url   = lighthouse_result["finalUrl"]

if total_bytes < 100_000:
    print(f"⚠ 実ページでない疑い: {final_url} ({total_bytes:,.0f}B)")
```

「やけに良いスコア」はまずこれを疑ってください。

## 落とし穴2：PSIは短時間の再リクエストにキャッシュを返す

スコアのブレ対策として「同じURLを3回計測して中央値を採る」実装にしたのですが、3回の値が**全サイトで完全に一致**しました。ブレがゼロ？　そんなわけがない。

`lighthouseResult.fetchTime`（実際に計測が走った時刻）を見ると：

```
1回目: fetchTime=2026-08-06T03:34:14.429Z score=72
2回目: fetchTime=2026-08-06T03:34:14.429Z score=72  ← 同一
3回目: fetchTime=2026-08-06T03:34:14.429Z score=72  ← 同一
（90秒待って）
4回目: fetchTime=2026-08-06T03:36:17.682Z score=73  ← ここで初めて再計測
```

**同じURLへの連続リクエストには、同一の計測結果（キャッシュ）が返ります。**再計測されるまでの間隔は、手元の観測ではおよそ90秒でした。

つまり「1件につき3回続けて呼ぶ」実装は、**1回の計測結果を3回受け取っているだけ**でした。ドキュメントには明記されておらず、`fetchTime` を見るまで気づけませんでした。

### 対策

1件ずつ繰り返すのをやめ、**全215サイトを1周してから次の周に入る**方式にしました。1周に30分ほどかかるので、周と周の間隔が自然に空き、キャッシュが無効になります。

```
for pass_no in 1..3:
    for site in all_sites:   # 全件を回してから次の周へ
        measure(site, pass_no)
consolidate()                # 最後に各サイトの中央値を確定
```

多数のURLを繰り返し計測する場合はこの順序が重要です。逆に「同じURLを何度叩いても課金・クォータが1計測ぶんで済む」という意味では、知っていれば便利な仕様でもあります。

## 落とし穴3：正しく3回測っても、4割のサイトは10点以上ばらつく

キャッシュを回避した「本物の3回計測」を210サイトで実施した結果です（モバイル）。

| 指標 | 値 |
|---|---|
| 3回の幅（最大−最小）の中央値 | 7点 |
| **幅が10点以上** | **42.4%** |
| 幅が20点以上 | 14.8% |
| 最大の幅 | **48点** |

実例を挙げると：

- あるテレビ局: **18点 → 3点 → 51点**
- あるチケット販売サイト: 9点 → 15点 → 52点
- ある政令市: 36点 → 69点 → 70点

同じURL、同じAPI、間隔は約30分。それでこの差です。PSIのモバイル計測は低速回線・低スペック端末のシミュレーションなので、サーバー側の状態や広告・埋め込みの内容次第でこれだけ動きます。

一方で、**210サイト全体の中央値は何度測ってもほぼ動きません**（52〜54点の範囲）。個々のブレは束ねると打ち消し合います。

### 実務への示唆

- **施策の前後比較を1回ずつの計測でやってはいけない。**10点の「改善」は42%の確率でただのノイズです
- 個別サイトのスコアは最低3回測って中央値を。集計値（中央値・合格率）なら1回でも信頼できる
- CI/CDでLighthouseのスコアをゲートにしている場合、閾値ぴったりの設定は誤検知します

## まとめ：一括計測パイプラインのチェックリスト

215サイトの定点観測で踏んだ穴をまとめると：

1. `total-byte-weight` と `finalUrl` を保存し、極小ページの満点を弾く
2. `fetchTime` の同一性を確認する。繰り返し計測は「全件1周してから次の周」
3. 個別サイトの値は3回計測の中央値。1回の値でランキングを作らない
4. それでも個別値には幅が残る。記事や報告には「何回計測の中央値か」を明記する

この仕組みで毎月、日本の有名サイト215件を業界別に定点観測しています。初回の調査結果（自治体67サイト編）は[こちらの記事](https://seoshindan.com/blog/municipal-website-speed-survey)にまとめています。

計測に使ったのは素の PSI API（無料枠: 25,000リクエスト/日）と SQLite だけです。同じような一括計測をやる方の参考になれば。
